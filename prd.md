# Product Requirements Document (PRD): Bid Protest Architect Skill & Interactive Workspace

## 1. Purpose and Scope

The Bid Protest Architect Skill provides an analytical toolkit and standalone interactive workspace (`dashboard.html`) for auditing federal government contract awards under the Federal Acquisition Regulation (FAR) and Government Accountability Office (GAO) Bid Protest Regulations (4 C.F.R. Part 21).

The product serves contracting officers, proposal managers, government contracts attorneys, and compliance analysts who need to evaluate solicitation terms against proposal submissions, Technical Evaluation Team (TET) consensus findings, Source Selection Decision Documents (SSDDs), and post-award debriefing records within tight statutory filing windows.

> **Legal Scope Notice**: Outputs generated by this toolkit assist analytical preparation and factual organization. They do not constitute legal advice or establish an attorney-client relationship. Formal filings require review by licensed procurement counsel.

---

## 2. Target Users and Core Use Cases

| User Group | Primary Objective | Key Workflow |
|---|---|---|
| **Capture & Proposal Managers** | Determine within hours of a debriefing whether evaluation flaws warrant escalating to outside protest counsel. | Load the RFP, proposal excerpts, and debriefing letter into `dashboard.html` or via agent prompt to verify mandatory compliance and 5-day CICA stay deadlines. |
| **Government Contracts Counsel** | Cross-reference solicitation clauses against contemporaneous agency records and organize draft GAO counts. | Run `scripts/bid_protest_analyzer.py` and `scripts/generate_protest_filing.py` on client documents to extract line citations, prejudice arguments, and 4 C.F.R. 21.3(c) document requests. |
| **Legal Operations & Analysts** | Diagnose document search recall across multi-volume procurement packages. | Execute `scripts/search_diagnostics.py` to compare natural-language, keyword, and boolean legal query retrieval performance. |

## 3. Functional Requirements

### 3.1 Multi-Format User Document Ingestion (`FR-01`)
- **CLI and Agent Ingestion** (`scripts/corpus_indexer.py`):
  - Must ingest user-specified directories (`--data`) or explicit file lists (`--files`) across `.md`, `.txt`, `.json`, `.csv`, `.tsv`, `.html`, `.htm`, `.xml`, `.docx`, and `.pdf` formats using the Python standard library by default.
  - Must classify each file into its procurement role (`solicitation`, `protester_proposal`, `awardee_proposal`, `tet_report`, `ssdd`, `debriefing`, `discussions`, `oci`, `cost_realism`, or `structured_bundle`).
  - Must extract solicitation identifiers, contract types, evaluation basis, Section L mandatory minimums, Section M factor weight hierarchies, offeror ratings/prices/metrics, and line-level source citations (`filename:L<line>`).
- **In-Browser Client-Side Ingestion** (`dashboard.html`):
  - Must allow users to drag-and-drop, select, or paste multiple procurement documents directly in the browser when `dashboard.html` is opened offline from disk or served over HTTP.
  - Must extract text client-side from `.md`, `.txt`, `.json`, `.csv`, `.tsv`, `.html`, `.xml`, `.docx` (via browser `DecompressionStream`), and `.pdf` streams, classify roles, accept optional metadata overrides, and recompute all audit views in memory.

### 3.2 Statutory Timeliness and Jurisdictional Gate (`FR-02`)
- **Deadline Calculation** (`TimelinessCalculator` in `scripts/bid_protest_analyzer.py` and client-side JS):
  - Compute the **5-calendar-day CICA Automatic Stay deadline** (`31 U.S.C. 3553(d)(4)`) from debriefing conclusion.
  - Compute the **10-calendar-day GAO Statutory Filing deadline** (`4 C.F.R. 21.2(a)(2)`).
  - Automatically roll deadlines falling on Saturday or Sunday to the next business day.
- **Interested Party Standing**:
  - Track offeror submission status, economic interest, and next-in-line eligibility under `4 C.F.R. 21.0(a)(1)`.

### 3.3 Dynamic 8-Ground FAR/GAO Cross-Examination (`FR-03`)
- Evaluate loaded corpora across all eight protest categories defined in `references/protest_grounds_taxonomy.md`:
  - `GR-01`: Unstated Evaluation Criteria (`FAR 15.303(a)(2)`, `FAR 15.305(a)`)
  - `GR-02`: Disparate / Unequal Treatment (`FAR 1.102-2(c)(3)`, `FAR 15.305`)
  - `GR-03`: Relaxation or Waiver of Mandatory Requirements (`FAR 15.206`, `FAR 15.305`)
  - `GR-04`: Flawed Past Performance Evaluation (`FAR 15.305(a)(2)`)
  - `GR-05`: Defective Best Value Cost-Technical Tradeoff (`FAR 15.308`, `FAR 15.101-1`)
  - `GR-06`: Misleading or Unequal Discussions (`FAR 15.306(d)`, `FAR 15.307`)
  - `GR-07`: Unmitigated Organizational Conflict of Interest (`FAR 9.504`, `FAR 9.505`)
  - `GR-08`: Flawed Cost or Price Realism Evaluation (`FAR 15.404-1(d)`)
- Apply an adversarial agency-defense red-team check and competitive prejudice verification (`404 F.3d 1346`), advancing grounds with viability scores `>= 80%`.
- Support `--grounds-json` and `--index-json` flags so external reasoning workflows can inject or merge structured findings.

### 3.4 Report, Pleading, and Retrieval Diagnostics Generation (`FR-04`)
- Emit `output/master_bid_protest_report.md` and `output/audit_results.json` via `scripts/bid_protest_analyzer.py`.
- Emit `output/gao_formal_protest_filing.md` formatted for GAO Electronic Protest Docketing System (EPDS) review via `scripts/generate_protest_filing.py`.
- Benchmark lexical vs. boolean legal query precision via `scripts/search_diagnostics.py`.
- Provide one-click browser export of structured JSON and Markdown GAO pleadings inside `dashboard.html`.

## 4. Dashboard Design and Technical Specification (`DESIGN.md` Alignment)

All interactive visual components in `dashboard.html` (compiled from `resources/templates/dashboard_template.html` via `scripts/build_dashboard.py`) adhere to [DESIGN.md](DESIGN.md):

### 4.1 Visual Hierarchy, Typography, and Layout
- **Typography**:
  - Serif display font (`Instrument Serif`) for top-level header display.
  - Sans-serif UI font (`DM Sans`) for prose, section labels, and interactive controls.
  - Tabular monospaced font (`IBM Plex Mono` with `font-variant-numeric: tabular-nums`) for all tables, numeric cells, dollar amounts, percentages, dates, and statutory citations, with right-aligned numeric columns.
  - Generic system defaults (`Inter`, `Roboto`) are excluded.
- **Single-Level Bento Grid**:
  - Flat 12-column CSS grid layout using solid surface tokens and `1px solid` borders (`6px` border-radius) with thin horizontal row dividers and zero nested card-in-card containers.
  - Gridlines are reserved strictly for quantitative chart axes and coordinate plots.

### 4.2 Light, Dark, and System Theme Architecture
- **Three-Button Segmented Theme Control**:
  - Top navigation bar control containing three textless SVG icon buttons side by side:
    - `#theme-btn-light` (`data-theme-mode="light"`, `title="Light Theme"`, `aria-label="Light Theme"`)
    - `#theme-btn-dark` (`data-theme-mode="dark"`, `title="Dark Theme"`, `aria-label="Dark Theme"`)
    - `#theme-btn-system` (`data-theme-mode="system"`, `title="System Theme"`, `aria-label="System Theme"`)
  - Active button state tracked via `.active` class and `aria-pressed="true"`, persisted in `localStorage`.
- **OS Appearance Detection**:
  - Browser layer tracks `window.matchMedia('(prefers-color-scheme: dark)')` with a real-time `'change'` event listener.
  - Backend compiler (`scripts/build_dashboard.py`) queries native OS preferences on macOS, Windows, and Linux and embeds `system_theme` as a fallback for restricted webviews.
- **Exact Theme Color Tokens**:
  - **Light Mode**: Background `#FAFAF9`, Surfaces `#FFFFFF`, Borders `#E7E5E4`, Primary Text `#1C1917`, Secondary Text `#787774`.
  - **Dark Mode**: Background `#0D0E11`, Surfaces `#16171D`, Borders `#292A30`, Primary Text `#ECE8E2`, Secondary Text `#9A9895`.

### 4.3 Semantic Data Visualization Palette and Interactive Views
- **Semantic Palette**:
  - Vibrant Teal (`#0D9488`): Primary series, protester baseline metrics, nominal links.
  - Energetic Amber (`#D97706`): Secondary series, warnings, statutory window urgency.
  - Vivid Indigo (`#4F46E5`): Solicitation baseline nodes and comparison series.
  - Functional Emerald (`#059669`): Passing metrics and validated viability states.
  - Deep Rose (`#E11D48`): Mandatory minimum violations, unstated penalties, and threshold breaches.
- **Interactive Relationship Node Map (3D + Software Projection Fallback)**:
  - Deterministic 3-tier spatial graph linking **Tier 1 (RFP Section L/M Clauses)** -> **Tier 2 (Proposal & TET/SSDD Findings)** -> **Tier 3 (Sustained GAO Protest Counts)**.
  - Uses hardware WebGL rendering paired with an automatic 2D projection fallback when WebGL is unavailable, supporting drag-to-orbit, zoom, pan, axis presets, hover inspection, and click-to-filter table synchronization.
- **2D Analytical Tradeoff Charts**:
  - Responsive SVG visualizations comparing **TET As-Evaluated vs. Lawful Compliant Factor Ratings** and **Evaluated Price vs. Weighted Technical Merit**, using transparent plot backgrounds and theme-matched axis gridlines (`#E7E5E4` light / `#292A30` dark).
- **Dynamic Incremental State & Optional SSE**:
  - Exposes `window.updateDashboardData(patch)` and optional Server-Sent Events (`/events` via `scripts/build_dashboard.py --serve`) to refresh data in place without resetting scroll position, active selections, or 3D camera angles.

## 5. Non-Functional Requirements and Verification Criteria

1. **Zero-Dependency Runtime Portability**: Core CLI scripts run on Python 3.9+ using standard library modules; `dashboard.html` executes offline from disk without external runtime dependencies.
2. **Relative Path Portability**: All scripts, templates, references, and documentation resolve paths relative to the repository root.
3. **Automated Test Coverage**: Unit and integration tests in `tests/test_analyzer.py`, `tests/test_search_diagnostics.py`, and `tests/test_dynamic_user_corpus.py` verify deadline math, multi-format user corpus parsing (`.docx`, `.html`, `.md`), all 8 protest ground categories, and `DESIGN.md` token/component compliance.
